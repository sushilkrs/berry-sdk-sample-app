# BerryDB SDK sample app

[![Open In Colab](https://colab.research.google.com/assets/colab-badge.svg)](https://colab.research.google.com/github/sushilkrs/berry-sdk-sample-app/blob/main/notebooks/walkthrough.ipynb)

A small student-document app that shows how to integrate with **hosted BerryDB** from your own backend
using the [BerryDB Python SDK](https://pypi.org/project/BerryDbNew/) (`BerryDbNew`).

Students are registered in the app, each with a **permanent UUID generated by the app**. A student can
upload several documents over time, and BerryDB keeps **one profile record per student** that is created
the first time and updated on every later upload.

When a student uploads a resume PDF, the app:

1. saves the file to `storage/students/<studentUuid>/documents/<documentUuid>/<file name>`;
2. records it in the app's **own** database (SQLite, `data/app.db`, table `documents`);
3. sends the PDF to BerryDB with `metadata = {studentId, documentId}`. BerryDB extracts **one structured
   resume record** (name, contact details, summary, skills, work experience, education) into the
   documents database and returns its id, which the app stores on its row;
4. rebuilds the student's merged profile from all of their documents and saves it with the SDK's
   `upsert`, using the student UUID as the record id: BerryDB creates it if it is new and replaces it if
   it exists;
5. on request, asks BerryDB to run **named-entity recognition** on a document's text. BerryDB saves the
   entities (people, organizations, locations, dates) on that document's record.

The UI labels every piece of information with where it comes from: the app's database, the BerryDB
documents database or the BerryDB profiles database.

Only a BerryDB API key is needed. BerryDB runs the AI for extraction and entity recognition.

## Try it in Colab

[`notebooks/walkthrough.ipynb`](notebooks/walkthrough.ipynb) runs the same flow step by step with nothing to
install: it creates the databases, registers two students, extracts sample resumes, builds and upserts their
profiles, runs NER, and shows two students uploading the same file. Its last (optional) cell starts the full
web app inside Colab. Open it with the badge above; you only need a BerryDB API key.

## Identity

| Key | Generated by | Identifies |
|---|---|---|
| Student UUID | this app, when the student is added | the student: app row, storage folder, `studentId` on every BerryDB document, id of the BerryDB profile |
| Document UUID | this app, on upload | one upload: app row, storage folder, `documentId` on the BerryDB document |
| BerryDB document id | BerryDB, from the database id and the file's SHA-256 | the extracted record of one file's content |

A student is never identified from a document's name, size, content or the name written inside it.

## How it talks to BerryDB

| Step | Call |
|---|---|
| Send a PDF for extraction | `POST /berrydb/ingest/structured`, multipart form with `database_name`, `file` and `metadata` (JSON). SDK 1.7.10's `Database.ingest_structured` accepts URLs only, so the app calls the endpoint directly to send the file itself. |
| Read document records | SDK: `db.get_all_documents(document_ids=[...])` |
| Create or update a student profile | SDK: `db.upsert([profile])` with `id` = student UUID (replaces the whole record, so the app always sends it complete) |
| Entity recognition | SDK: `db.ner("content.text", document_ids=[id], annotate=True)` |
| Delete a record | SDK: `db.delete_document(id)` |
| Search students in plain English | SDK: `LLMAgent.chat(llm_api_key, {"question": ...})` writes a query, then `db.query(sql)` runs it (see below) |
| Knowledge graph of a student | `GET <BERRYDB_HOST>/universal-api/graph/enrich?database=...` (BerryDB's graph of the documents' entities), joined with the profile; falls back to each document's NER annotation |

All BerryDB calls live in [`backend/berry_client.py`](backend/berry_client.py); the merge rules in
[`backend/profile_merge.py`](backend/profile_merge.py).

## Searching students

The Search page takes a plain-English question, for example "students who know Java and MySQL", and lists
every matching student. It searches the merged profiles only, and skills only in `skillsList`.

1. **Berry GPT writes the query.** `LLMAgent.chat()` sends the question to Berry GPT with the app's own LLM
   key (`LLM_PROVIDER`, `LLM_API_KEY` in `.env`). Berry GPT only passes the prompt to the LLM; it does not
   see the database, so the system prompt carries the `StudentProfileSchema` and the query rules. The
   question goes in through the `{{question}}` placeholder.
2. **The app checks it.** One SELECT, no subqueries, and a WHERE of the form
   `p.databaseName = "StudentProfiles" AND (...)`: all databases share the `BerryDb` bucket, so without that
   scope a query would read every database the API key can see.
3. **`db.query()` runs it** and returns every matching document, not only the most similar few. It returns
   an empty string on failure, so the app keeps the reason it prints and shows it.

The page shows the query that was run and the model's reply. Berry GPT treats temperature 0 as unset, so
the app sends 0.01; and its default Anthropic model name is not a valid one, so the app always sends a model.
The code is in [`backend/student_search.py`](backend/student_search.py).

## Merge rules for the student profile

- Name and email entered when the student was added always win (email falls back to the newest document).
- Other single values (job title, location, summary, links): the most recently **uploaded** document with a value wins.
- Skills, work experience and education are combined across documents; work experience keeps one entry per
  company (newest description). Each entry records which document it came from.
- The profile is rebuilt from scratch after every upload, re-send and delete, so removing a document removes
  what only that document contributed.

## Identical files from different students

The app compares a new upload only with the **same student's** files (by SHA-256) and refuses an exact
re-upload. Different students are never compared, so two students may upload the same file.

BerryDB derives a document's record id from the file content, so identical files from two students land on
**one** BerryDB document record; the later upload re-tags it with its own `studentId` and replaces its
entity annotations. Each student's profile is still built separately and stays correct. The app marks such
documents as "Shared record" and keeps the BerryDB record until no student uses it.

## Getting started

Requirements: Python 3.11 or later and a BerryDB API key (from your account settings at
[app.berrydb.io](https://app.berrydb.io)).

```bash
python -m venv .venv
.venv/Scripts/python -m pip install -r backend/requirements.txt     # macOS/Linux: .venv/bin/python
cp .env.example .env                                                # then put your API key (and an LLM key, for search) in .env
.venv/Scripts/python -m backend.berry_setup.create_schema_and_database   # once per BerryDB organization
.venv/Scripts/python -m backend                                     # open http://127.0.0.1:8800
```

The setup step registers `ResumeSchema` and `StudentProfileSchema` and creates the databases
`ResumePlaygroundKG` (one record per document) and `StudentProfiles` (one record per student) in your
organization. It skips anything that already exists, so it is safe to run again. The SDK host is
`https://api.berrydb.io`; `app.berrydb.io` is the web app, not the API.

## Where data lives

| What | Where |
|---|---|
| Uploaded files | `storage/students/<studentUuid>/documents/<documentUuid>/<file name>` |
| Students, documents and processing status | SQLite `data/app.db`, tables `students` and `documents` |
| Extraction, full text and entities of each file | BerryDB `ResumePlaygroundKG` (schema `ResumeSchema`) |
| One merged profile per student | BerryDB `StudentProfiles` (schema `StudentProfileSchema`), record id = student UUID |

`ResumeSchema` declares a `content.text` field. Structured ingest stores the full resume text there, and
BerryDB's entity recognition only runs on fields the schema declares.

To browse the app database, open `data/app.db` with any SQLite viewer, for example the
SQLite Viewer extension for VS Code or DB Browser for SQLite.

## Knowledge graph

The student page ends with a **Knowledge graph** card: the student, their skills, job title, location,
companies and education from the merged profile, their documents, and the people, organizations and
places each document mentions. Entities that name the same thing as a profile value (the organization
"Infosys" in a resume and the company "Infosys" in the profile) are one node. The data comes from
`GET /api/students/<id>/graph` ([`backend/graph.py`](backend/graph.py)); the card is
[`frontend/js/graph.js`](frontend/js/graph.js), drawn with the vendored
[force-graph](https://github.com/vasturiano/force-graph) library.

Entities come from BerryDB's graph service when it has projected the document, otherwise from the
document's own NER annotation, so run entity recognition on a document to see its entities.

## Limitations

- PDF only, up to 50 MB per file. Scanned PDFs without a text layer are rejected by BerryDB.
- BerryDB reads are eventually consistent: a record written a moment ago may not be readable yet. The app
  reads by id and retries briefly; the UI refreshes while work is in progress.
- Re-sending a file replaces its BerryDB document record, including any entity annotations; run entity
  recognition again afterwards.
